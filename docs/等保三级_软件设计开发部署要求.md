> 依据：GB/T 22239-2019《信息安全技术 网络安全等级保护基本要求》第 8 章“第三级安全要求”（8.1 安全通用要求；8.2～8.5 扩展要求）。
> 条款号均对应标准原文。附件 PDF 的文字层是加密字体，内容通过 OCR 提取，个别字词经人工校正。
>
> **约定**：
> - 【标准】= 标准原文要求（必须满足）
> - 【建议】= 为落实标准而提出的工程化做法或参数。标准本身**没有**规定具体数值，这些是建议，需由甲方或测评机构确认

## 1. 开发软件需要满足的信息安全三级要求

### 1.1 开发过程管理要求（8.1.9.4 自行软件开发 / 8.1.9.5 外包软件开发）

| 条款 | 【标准】要求 | 可操作落地措施【建议】 | 交付证据 |
|---|---|---|---|
| 8.1.9.4 a) | 开发环境与实际运行环境**物理分开**，测试数据和测试结果受控 | 开发 / 测试 / 生产使用独立物理网络或独立账号和独立 VPC；生产数据进入测试前必须脱敏；测试报告纳入受控文档库 | 环境拓扑图、脱敏规程、测试数据审批单 |
| 8.1.9.4 b) | 制定软件开发管理制度，明确过程控制方法和人员行为准则 | 发布《软件开发安全管理制度》（模板见 1.4.1） | 制度文件及发布记录 |
| 8.1.9.4 c) | 制定代码编写安全规范，开发人员参照执行 | 发布《安全编码规范》（模板见 1.4.2），在 CI 中由 SAST 规则强制检查 | 规范文件、扫描报告 |
| 8.1.9.4 d) | 具备软件设计文档和使用指南，并控制文档使用 | 设计说明书、安全设计说明书、用户手册、运维手册纳入文档库，按权限访问 | 文档清单、访问权限记录 |
| 8.1.9.4 e) | 开发过程中进行安全性测试；**安装前检测恶意代码** | 流水线集成 SAST、SCA（第三方组件漏洞）、DAST；发布制品做防病毒扫描并记录哈希值 | 各类扫描报告、制品哈希值 |
| 8.1.9.4 f) | 程序资源库的修改、更新、发布须经授权批准，严格版本控制 | Git 保护分支 + MR/PR 强制评审（至少 1 人）+ 发布审批；制品库只允许 CI 写入 | 评审记录、发布审批单、Tag 记录 |
| 8.1.9.4 g) | 开发人员为专职人员，开发活动受控、被监视、被审查 | 代码仓库账号实名且与工号绑定；记录并定期审查代码库访问日志；离职当天回收权限（呼应 8.1.8.2） | 人员名单、权限审查记录 |
| 8.1.9.5 a) | 外包：交付前检测恶意代码 | 外包交付物入库前由甲方做病毒扫描和 SCA 扫描 | 检测报告 |
| 8.1.9.5 b) | 外包：提供设计文档和使用指南 | 写入合同交付清单 | 交付清单 |
| 8.1.9.5 c) | 外包：**提供源代码**，审查后门和隐蔽信道 | 合同约定交付源代码；甲方或第三方做代码审计，重点检查硬编码账号、隐藏接口、未声明的外联地址 | 源码审计报告 |
| 8.1.9.7 b) | 上线前做安全测试，报告**包含密码应用安全性测试**内容 | 渗透测试 + 密码应用测试（算法、密钥管理、随机数）【待确认 M6】 | 安全测试报告 |
| 8.1.9.8 | 交付清单、运维培训、建设过程文档和运维文档 | 按 1.4.4 交付清单执行 | 交接签字单 |

### 1.2 软件必须实现的安全功能（来自 8.1.4 安全计算环境、8.1.5 安全管理中心）

下表是需要**写进代码**的功能点，可直接作为开发任务清单：

| 编号 | 条款 | 【标准】要求 | 开发实现要点【建议】 |
|---|---|---|---|
| D-01 | 8.1.4.1 a) | 用户身份标识唯一，鉴别信息有复杂度要求并定期更换 | 用户名全局唯一且不可复用；密码策略可配置（建议：长度≥8，至少包含 3 类字符，有效期≤90 天，不得与最近 N 次重复）；首次登录强制修改密码 |
| D-02 | 8.1.4.1 b) | 登录失败处理：结束会话、限制非法登录次数、超时自动退出 | 连续失败 N 次（建议 5 次）后锁定账号或 IP 一段时间（建议 ≥10 分钟）；会话空闲超时（建议 ≤30 分钟）自动注销；登录失败提示不区分“用户不存在”和“密码错误” |
| D-03 | 8.1.4.1 c) | 远程管理时防止鉴别信息被窃听 | 全站 HTTPS（TLS1.2 及以上，或国密 TLCP【待确认 M6】）；前端传输口令时不得明文或使用可逆编码 |
| D-04 | 8.1.4.1 d) | **两种或以上鉴别技术组合，其中一种必须是密码技术** | 口令 + 数字证书 / UKey / 基于 SM3、SM4 的动态令牌（OTP）等；**短信验证码是否算作密码技术需与测评机构确认**【待确认 M6/M7】 |
| D-05 | 8.1.4.2 a)c) | 分配账户和权限；及时删除或停用多余、过期账户；禁止共享账户 | 账户生命周期管理（创建、启用、停用、删除）；长期未登录账户自动停用（建议 90 天）；账户有效期字段 |
| D-06 | 8.1.4.2 b) | 重命名或删除默认账户，修改默认口令 | 不内置固定口令的 admin；初始化时由安装向导设置管理员账号和口令 |
| D-07 | 8.1.4.2 d) + 8.1.5.1～8.1.5.3 | 管理用户最小权限，**三权分立**（系统管理员、审计管理员、安全管理员） | 内置三类管理角色且互斥：系统管理员管理用户和配置，安全管理员管理策略和授权，审计管理员只能查看审计日志；任何一个角色都不能同时拥有另两类权限 |
| D-08 | 8.1.4.2 e)f) | 由授权主体配置访问控制策略；粒度：主体到用户级或进程级，客体到文件、数据库表级 | RBAC/ABAC；每个接口在后端做鉴权（禁止只靠前端隐藏菜单）；防越权：数据查询带上属主或租户条件 |
| D-09 | 8.1.4.2 g) | 对重要主体和客体设置**安全标记**，控制对带标记资源的访问 | 在数据和用户上增加密级或敏感级字段，按“用户级别 ≥ 数据级别”控制访问；标记由安全管理员设置（8.1.5.3 b)） |
| D-10 | 8.1.4.3 a)b) | 审计覆盖每个用户；记录日期时间、用户、事件类型、是否成功等 | 统一审计组件，至少记录：登录登出、鉴权失败、权限变更、用户管理、配置变更、敏感数据的查询和导出、审计策略变更。字段格式见 2.5.3 |
| D-11 | 8.1.4.3 c)d) | 保护审计记录，定期备份；**保护审计进程不被未授权中断** | 审计表只允许追加，应用账号没有删改权限；日志实时外发到日志服务器或 SOC；审计服务异常时告警；建议用哈希链防篡改 |
| D-12 | 8.1.4.4 d) | 数据有效性检验：人机接口和通信接口的输入符合设定要求 | 所有入参在服务端校验（类型、长度、格式、白名单）；防 SQL 注入（参数化查询）、XSS（输出编码）、命令注入、路径穿越、XXE、SSRF；文件上传校验类型和大小，存放在 Web 目录之外 |
| D-13 | 8.1.4.4 c) | 限制管理终端的接入方式或网络地址范围 | 管理后台支持配置 IP 白名单；管理端口与业务端口分离 |
| D-14 | 8.1.4.4 e) | 发现已知漏洞并及时修补 | 引入 SCA，依赖组件的高危漏洞禁止发布；建立组件清单（SBOM） |
| D-15 | 8.1.4.7 | 重要数据传输和**存储**过程中的完整性（校验技术或密码技术） | 传输：TLS；存储：对关键数据和配置计算 HMAC-SM3 / SHA-256 并在读取时校验【待确认 M4】 |
| D-16 | 8.1.4.8 | 重要数据传输和**存储**过程中的保密性（密码技术） | 口令使用加盐慢哈希（如 PBKDF2、bcrypt、SM3 迭代）；重要业务数据和个人信息采用字段级加密（SM4 / AES）；密钥不得硬编码，由 KMS 或密码机管理【待确认 M6】 |
| D-17 | 8.1.4.9 a) | 本地数据备份与恢复功能 | 提供备份、恢复脚本或功能，并验证可恢复 |
| D-18 | 8.1.4.10 | 鉴别信息、敏感数据的存储空间释放前完全清除 | 会话销毁时清除 Token 和缓存；敏感对象使用后清零（如 char[]/byte[]）；临时文件用后安全删除；注销时清除前端本地存储 |
| D-19 | 8.1.4.11 | 只采集必需的个人信息；禁止未授权访问和非法使用 | 字段最小化；展示时脱敏（手机号、身份证号打码）；个人信息的查询和导出单独授权并审计 |
| D-20 | 8.1.4.6 / 8.1.4.5 | 可信验证（“可”选）；防恶意代码或主动免疫 | 发布包签名，启动时校验完整性；关键配置文件校验哈希，被篡改时告警并写审计日志 |
| D-21 | 8.1.5.1～8.1.5.3 a) | 三类管理员必须经身份鉴别，只能通过**特定命令或操作界面**操作，且操作被审计 | 独立管理入口，不开放直连数据库改数据的“后门”；三员的所有操作全部审计 |

## 2. 设计软件需要满足的信息安全三级要求

### 2.1 设计原则（来自 8.1.9.2 安全方案设计）
- 【标准】8.1.9.2 a)：先按等级选择基本安全措施，再按**风险分析**结果补充或调整。设计阶段需要输出威胁建模或风险评估。
- 【标准】8.1.9.2 b)：安全整体规划和安全方案**必须包含密码技术相关内容**，并形成配套文件。
- 【标准】8.1.9.2 c)：方案需经相关部门和安全专家**论证审定、批准后实施**。设计评审要留存记录。

### 2.2 安全架构设计（“一个中心、三重防护”）

标准的技术要求按以下结构组织，软件架构应与之对应：

```
┌────────────────────── 安全管理中心 (8.1.5) ──────────────────────┐
```
